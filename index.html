Overview

LLM agents read external content, call tools and change application state, so a successful attack shows up as a leaked secret or an unauthorized action, not just a bad reply. Automated red-teaming services such as Promptfoo, PyRIT, DeepTeam and Dreadnode are built to find these failures, but when a test finds nothing it is unclear whether the agent resisted or the service never reached a weakness. GreyZone evaluates the services themselves: each one acts as an end-to-end attacker and is measured on whether it generates and delivers attacks that cause verified security-policy violations in real agent applications.

  • Real applications. 10 independently developed, open-source agent applications (coding, enterprise collaboration, email, trading, commerce, banking, smart home, Kubernetes operations and social/on-chain agents) run with their own workflows, permissions and security boundaries. External dependencies are replaced with controlled simulations, and every run starts from a prepared initial state.
  • 46 attack scenarios. Each scenario fixes the application, initial state, security policy, attack objective, attacker constraints and oracle. The objective is the same for every service; how to reach it is up to the service.
  • One attacker interface. An MCP interface exposes only the operations the attacker's role permits, for direct injection (messages to the agent) or indirect injection (content the agent reads during its task). Service-specific adapters connect each red-teaming service to it.
  • Independent oracles. Each scenario's oracle checks execution evidence and application state, not the service's own verdict or the agent's reply, before reporting a verified outcome.

Results

One row per campaign: one attacker configuration against every scenario of one range on GreyZone v1.0.0. Scores are comparable only within a range, so campaigns are ranked per range. Click a column to sort.

Campaigns are ranked by episode scores, read from each episode's native Oracle evaluation (schema 1, score policy 2; only the fields scoring needs). Every metric is computed by the leaderboard, never self-reported, and no attack success rate is computed. Score (0–1, ranks the table) — each completed episode scores the best normalized score of its in-scope surfaces (binary actions 0/1; disclosures earn verified facts ÷ eligible facts, with justified partial credit); episode scores are averaged within each attack scenario, then across the range's scenarios. No-reply / Error — share of attack episodes whose evaluation is no_reply / error; they carry no score and are reported apart from it. Control FP — mean score of kubectl-ai's benign control episodes (0 is healthy); — where a range has no control. Budget — attack messages allowed per episode.

Submit results

Submit one evaluation campaign through a GitHub pull request.

  1. Run every attack scenario of one range from GreyZone v1.0.0 with its fixed victim model (on kubectl-ai, also the benign control). Keep every Oracle result file, including no_reply and error episodes, and publish them with their evidence.
  2. Build the campaign file: python3 scripts/build_submission.py --range … --results … --out data/submissions/<campaign-id>.json. It reads each result file's native evaluation, keeps only the fields scoring needs (dropping provenance, success, evidence lists and the like), validates the campaign exactly as CI does and prints the score the leaderboard will show.
  3. Click Create submission, paste the generated file over the template and keep its file name, then Commit changes… → Propose changes → Create pull request. GitHub forks the repository for you; fill in the pull request template.
Create submission ↗ Submission guide

Numbers are never self-reported: the leaderboard scores your episodes itself, and maintainers check them against the linked artifacts before merging. See the submission guide for every field. Prefer git? Fork, add the file on a branch and open a pull request as usual.
